## スライド4: 方位磁石センサーの基礎（9-15分）

### ビジュアル表現（黒板またはスライド）
```
磁気コンパスの原理
地球の磁場 ─→ [micro:bit磁気センサー] ─→ 0～359度 の数値

度数での方位表記（例）
        0° (北)
         ↑
         N
    NW   |   NE
 315°    |    45°
    ╱────┼────╲
   ╱ 270°│ 90°╲   東
西──      │      ──
   ╲     │     ╱
    ╲────┼────╱
   225°  │  135°
    SW   |   SE
         ↓
         S
       180°
```

### 講師スクリプト（タイムキープ: 6分）
皆さんのポケットには、小さな磁石のセンサーが隠れています。
（micro:bitを見せる）

このセンサーは、地球全体を覆う磁場を感知します。
北から時計回りに、0度から359度までを測ります。

**なぜ360度ではなく0～359度か？**
ミリオンダラークエスチョン！
実は、360度になると0度と重なるからです。
プログラムでは0度を2回数えないように、0～359度で表現することがルール。

**では、これを8つの方角に分類するには？**
例えば、北（N）は何度から何度まで？
（学習者に考えさせる時間を取る）

正解は、0度を中心に±22.5度です。
つまり「337.5度以上359度」「0度以上22.5度未満」
ただし、プログラムでは「0度以上22.5度」「337.5度以上359度」と書きます。

なぜこんなルールが必要か。それは「ルールが曖昧だと、プログラムの結果も曖昧になる」から。
プログラミングは「ルール作り」の芸術です。

## スライド5: 67.5度の謎（15-20分）

### 問い
「もし67.5度なら？」

### 講師スクリプト（タイムキープ: 5分）
67.5度は、北東（NE=45度）と東（E=90度）の真ん中です。
（スライドまたは黒板で矢印を描く）

```
45°(NE) ─────[67.5°]───── 90°(E)
```

「えっ、中間だったら、どっちにする？」

そう、正確に言うと「ルール次第」。
今日のプログラムでは、次のルールを採用しています：
- 45度以上67.5度未満 → NE（北東）
- 67.5度以上90度未満 → E（東）

つまり「67.5度はEに分類される」。

なぜこのルール？
数学では「未満（<）と以上（≥）」の組み合わせで、重複や隙間なくカバーするのが定石。
各方角8個、22.5度ずつ。NはNEの直前、SEはEの直後、という順序で切る。

このルール、テストケースでめっちゃ出てきます。
そしてプログラマーはよくここでバグを仕込みます。「あ、<と≤を間違えた」とか。

## スライド6: 実機での校正の意味（20-25分）

### ビジュアル
```
校正なし（赤いX）        校正済み（緑のチェック）
↓                        ↓
磁場の干渉受けやすい      その場所に合わせた調整完了
正確さ: ±20度以上        正確さ: ±2～3度
```

### 講師スクリプト（タイムキープ: 5分）
先ほどの実験で「校正」という操作が出てきました。

磁気センサーは、その場所の磁場を「基準」にして動きます。
例えば、スピーカーの近くだと、その磁場を基準にしてしまい、正確さが大きく低下します。

だから「この場所で正確に測りたい」なら、先にセンサーを全方向回して「この場所の磁場地図」をセンサーに教える必要がある。
それが「校正」。

校正が終わると、センサーは「あ、この場所ではこの磁場が北なんだな」と理解して、正確に方角を返すようになります。

もし学習者が「うちのセンサーおかしい、いつも南と表示される」と言ったら？
**第一の対策: 校正をやり直す**
外の同じ場所で、もう一度校正を実行する。
それでだいたい直ります。

## スライド7: テストと実機の違い（25-30分）

### ビジュアル
```
TypeScriptテスト              実機での動作
「入力: 0度」                 「実際に0度に向けた」
  ↓                            ↓
「期待: 'N'」               「校正精度: ±2度」
  ↓                            ↓
「結果: 'N'」               「実測: 357～3度」
✓パス                         ✓パス（多くの場合）
```

### 講師スクリプト（タイムキープ: 5分）
ここが大事な気づき。

**テスト** は「入力→処理→出力」の理屈を確認する。
入力が確実に与えられるから、出力も確実に期待値になる。

**実機** は「センサーのばらつき」が存在する。
磁石があるのか、スピーカーの近くなのか、その場所の環境に影響される。

だから「テストが全部パス ≠ 実機で完全に動く」

テストは必要だが、テストだけでは不十分。
実機での動作確認も欠かせない。

これを「テスト駆動開発の限界」と言う研究者もいます。
でも「テストがあれば、少なくとも論理的なバグは防げる」というメリットもある。

ベストプラクティスは「両方やる」ことです。

## スライド9: 意図的なバグ注入演習（40-50分）

### ビジュアル
```
元のコード                修正版（バグ入り）
const headingToDirection   const headingToDirection
  if (heading < 22.5) ✓      if (heading <= 22.5) ✗
  ...                        ...

何が違う？ heading = 22.5 の時
元版: NE（正解）
修正版: N（間違い）
```

### 講師スクリプト（タイムキープ: 10分）
では、実際に「バグを仕込んだコード」を書いてみましょう。

学習者と一緒に行う：
1. `sample-compass-ts/src/compass.ts`を開く
2. 22.5度の判定を `<` から `<=` に変える（故意にバグを入れる）
3. テストを実行：`npm test`
4. **何が起こるか？**

テストが失敗します。赤い X が表示。

**講師の説明**:
> 見てください。このテストが「22.5度はNEではなくNだ」と主張しています。
> つまり、元のコードが正しかったんですね。

ここで学習者に考えさせます：
「では、このバグを修正するには、どこを直す？」

答え：元に戻す。`<=` を `<` に戻す。

テストを再度実行：パス。

**より難しいバグを仕込む例:**
```typescript
// 元のコード（正解）
const headingToDirection = (heading: number): Direction => {
  if (heading < 22.5 || heading >= 337.5) return 'N';
  if (heading < 67.5) return 'NE';
  // ...
};

// バグ版：北の範囲を「337.5」から「335」に変える
// これは、たったの2.5度のズレ。
// でも テストで「heading = 336 度」をチェックしていれば、引っかかる
```

## スライド10: 100%カバレッジの落とし穴（50-60分）

### ビジュアル
```
カバレッジ100%とは
「すべてのコード行が、テストで実行された」

でも...

┌────────────────────────────────────┐
│ カバレッジ100% ≠ バグゼロ       │
└────────────────────────────────────┘

例：
if (heading < 22.5) return 'N';  ← テスト実行済み
else return '???';                 ← このelseが間違ってる

テストが「heading < 22.5」のケースだけ確認したら？
→ else内の間違いに気づかない
```

### 講師スクリプト（タイムキープ: 10分）
ここからが、品質保証の哲学です。

**カバレッジ** という言葉を聞いたことがあるかもしれません。
「すべてのコード行をテストで実行した」という意味。

100%カバレッジなら「すべてのコードが試された」「バグはない」と思いたいですね。

でも、実際には？

（スライドの例を指す）

```
if (heading < 22.5 || heading >= 337.5) return 'N';
```

テストケース「heading = 0」を実行 → この行は実行される ✓

でも、テストケースに「heading = 359」がなかったら？
実は「337.5」の判定がバグってるのに、気づかない。

カバレッジが100%でも、「テストケースの質」が低いと、バグが隠れる。

**では、どうする？**

1. **境界値テスト**: 境界ギリギリの値をテストする
2. **同値分割**: 値をグループ分けして、各グループから1つ選ぶ
3. **決定表テスト**: 複数条件の組み合わせをテストする
4. **実機テスト**: シミュレーターでは不可視なバグを探す

これら全部を組み合わせることで、初めて「バグが少ない」に近づく。
