# 90分ワークショップ: micro:bit方位磁石と自動テスト

MakeCodeで動きを観察し、PythonとTypeScriptで同じ問題を検証する授業案です。

**対象**: プログラミング入門を終えた小学5年生以上  
**定員**: 1名から30名程度  
**必要な環境**: コンピューター、ブラウザ（MakeCode Webは必須ではありません）

## 到達目標

終了時に学習者は次を説明・実行できます。

- **方位角と8方位の関係を図で説明できる**（0〜359度がどの方位になるか）
- **3つの言語が同じ問題を解いていることに気づける**
- **「テストが通る」と「実機で動く」の違いを説明できる**
- **1つ新しいテストを書き、失敗→修正→成功の流れを体験できる**
- **カバレッジ100%でもバグが完全にゼロにならない理由を答えられる**

## 準備（講師向け）

授業前に環境を用意します（学習者は見る必要なし）:

```bash
npm ci
npm --prefix projects/sample-compass-ts ci
npm --prefix projects/sample-compass-makecode ci
uv sync --project projects/sample-compass
npm run test:all
npm run build:hex
```

**ネットワークの準備**:

授業中に MakeCode Web を使う場合は、通信が安定していることを確認。不安定なら、講師が準備段階で画面を録画して、授業中に共有してください。

**実機を使う場合**:

- micro:bit V1 または V2
- USB ケーブル
- 磁石から離れた、屋外の校正スペース

**実機がない場合**:

シミュレーターだけでも学習できます。ただし、最終段階（88-90分）は、講師が準備段階で試して、「こう動きます」と説明する形になります。

**学習者の環境**:

2 人 1 台でも進行できます。その場合は、操作と観察を交代してください。

**⚠️ 時間管理のコツ:**

この時間表は目安です。実運用では以下の調整が効果的です:

- **時間がギチギチな場合**: 30～50分の TypeScript テストを「コピペ」で進行させる（手入力では 2-3分余計にかかる）
- **80～88分が足りなくなった場合**: 実機校正をスキップして、シミュレーター画面を講師が映して「こう動きます」と説明する

## 0〜10分: 導入

ルートREADMEの「方位磁石とは何か」を見せます。

**講師の説明**:

> micro:bit には磁気センサーが入っています。北がどこにあるか教えてくれます。
> 返ってくる値は「方位角」という0から359の数字です。

**黒板に書く**（または画面に表示）:

```
  0°  = 北（N）
 45°  = 北東（NE）
 90°  = 東（E）
135°  = 南東（SE）
180°  = 南（S）
225°  = 南西（SW）
270°  = 西（W）
315°  = 北西（NW）
```

**問い**: 

> 「もし 67.5 度だったら、東（E）と南東（SE）のどちらにしますか？」

学習者に考えさせて、「45度〜90度の間なら東北東...という詳しい分類もあるけど、今回は8方位に決める」と説明します。

**チェックポイント**: 学習者が「北だけ 0 度を中心に左右に広がっている」ことに気づき、図で説明できる。

## 10〜30分: MakeCode で観察

**講師が実演**（学習者はそれを見ていても、自分の PC で一緒に操作してもいい）:

1. [`sample-compass-makecode/src/main.ts`](../../projects/sample-compass-makecode/src/main.ts) を MakeCode で開く
2. ブロックの中から「A ボタンが押された」「ずっと（forever）」を探す
3. [`compass.ts`](../../projects/sample-compass-makecode/src/compass.ts) の `input.compassHeading()` ブロックを探す

**講師の説明**:

> `input.compassHeading()` は「磁気センサーから方位角を読む」命令です。
> 注意：`input.acceleration` は「傾き」を読むので、方位磁石とは違います。

**実行**:

```bash
npm --prefix projects/sample-compass-makecode test
```

末尾に `MAKECODE_TEST_RESULT: all passed ✓` が出たことを確認します。

ナレーション:

> テストが全部通ったということは、ブロックが正しく8方位に分類できたということです。
> でも、このテストは**シミュレーター上**での実験なので、本物のセンサーの精度までは保証できません。

**実機がある場合**（オプション）:

生成済み HEX を micro:bit に書き込み、A ボタンで校正して、実際に回転させます。磁石やスピーカーから離して、屋外で校正することを勧めます。

## 30〜50分: TypeScript で境界値テストを追加

**講師の説明**:

> TypeScript は「型（かた）」という仕組みを使って、プログラムが返せる値を制限できます。
> 東（E）と南東（SE）の境界は 67.5 度です。その直前と直後をテストすると、バグが隠れにくいです。

**学習者の作業**:

1. [`sample-compass-ts/test/compass.test.ts`](../../projects/sample-compass-ts/test/compass.test.ts) を開く
2. 次のコードを探す:

```typescript
test('heading from 0 to 89.9...', () => {
  // 既存のテスト
});
```

3. その下に新しいテストを追加する:

```typescript
test('67.5 度の直前と境界を判定する', () => {
  expect(Compass.headingToDirection(67.49)).toBe('NE');  // 22.5 <= 67.49 < 67.5 => NE
  expect(Compass.headingToDirection(67.5)).toBe('E');    // 67.5 <= 67.5 < 112.5 => E
});
```

4. テストを実行する:

```bash
npm --prefix projects/sample-compass-ts test
```

**何が起こるか**:

- ✅ 成功したら、このテストは既に正しく実装されていることが分かります
- ❌ 失敗したら、プログラムにバグがあります

**講師の説明**:

> このテスト 1 つで、グレーゾーン（どちらでもあり得そう）の部分を確実にしました。
> 発見したバグは、修正することで正確さが上がります。

**早めに終わった学習者向け**:

`-1`、`360`、`NaN` といった「ありえない値」をテストして、プログラムがどう対応するか確認します。

## 50〜65分: MakeCode Python と TypeScript を比較

**講師の説明**:

> さっきのテストに成功しました。でも、シミュレーター上での成功と、実機での成功は別です。
> MakeCode Python は実機の磁気センサーを読みます。
> TypeScript はコンピューター上で、センサーなしで「もし方位角が 45 度なら？」と仮説をテストします。
> この 2 つの役割を区別することが大事です。

**比較作業**:

1. [`sample-compass/src/compass_makecode.py`](../../projects/sample-compass/src/compass_makecode.py) を開く
2. [`sample-compass-ts/src/compass.ts`](../../projects/sample-compass-ts/src/compass.ts) と並べる
3. 差を探す：

- Python: `return "N"` （文字列）
- TypeScript: `Direction = 'N' | 'NE' | ...` （型で縛られた文字列）

**講師の説明**:

> TypeScript の「型」システムが「あり得ない答え」を防ぎます。
> MakeCode Python はそこまでの保護がないので、テストでカバーする必要があります。

**ビルド**:

```bash
npm --prefix projects/sample-compass-ts run build
```

ビルド成功 = TypeScript の型チェック OK

## 65〜80分: 品質チェック（テストが本当に役に立つか確認）

**講師の説明**:

> テストを書いたら、それが本当に効く（バグを見つける）かテストします。
> 不具合を作って、テストが見つけてくれるか確認しましょう。

**講師の操作**（学習者は見ていても、自分でやってもいい）:

1. 学習用ブランチを作る:

```bash
git checkout -b practice/test-failure
```

2. [`../../projects/sample-compass-ts/test/compass.test.ts`](../../projects/sample-compass-ts/test/compass.test.ts) で、さっき追加したテストの期待値を一時的に間違える:

```typescript
test('67.5 度の直前と境界を判定する', () => {
  expect(Compass.headingToDirection(67.49)).toBe('E');   // ← 意図的に間違える（NE ではなく E）
  expect(Compass.headingToDirection(67.5)).toBe('E');
});
```

3. テストを実行する:

```bash
npm run test:all
```

**何が起こるか**:

```
FAIL: 67.5 度の直前と境界を判定する
Expected: E
Received: NE
```

❌ テストが失敗します。

**講師の説明**:

> テストが「本当に間違いを見つけた」ということです。テストがいなかったら、このバグは本番までに気づかなかった可能性があります。

4. 期待値を戻す:

```typescript
test('67.5 度の直前と境界を判定する', () => {
  expect(Compass.headingToDirection(67.49)).toBe('NE');  // ← 正しい値に戻す
  expect(Compass.headingToDirection(67.5)).toBe('E');
});
```

5. テストを実行する:

```bash
npm run test:all
```

✅ 全テスト成功。

**講師の説明**:

> 「テスト → 失敗 → 修正 → 成功」という流れが大事です。
> この循環（サイクル）で、バグは修正され、プログラムは正確になります。

**チェックポイント**: 学習者が「テスト = 間違いを見つける道具」だと理解できているか、言葉で説明させます。

## 80〜88分: 実機またはシミュレーターで確認

**講師の説明**:

> テストがすべて成功しました。でも最後は「本当に動くか」を目で確認します。

### 実機を使う場合

```bash
npm run build:hex
```

生成されたファイル（`sample-compass-makecode/built/binary.hex`）を micro:bit に転送します。

**確認**:

1. A ボタンで校正（北の方向に向ける）
2. B ボタンで状態確認
3. 実際に本体を回転させて、LED がその方位を指すか見る

**重要**: 校正は磁石やスピーカー、金属から離れた屋外で行うことを推奨。

### 実機がない場合

```bash
npm run build:hex
```

は実行できなくても（MakeCode Web がなくても）、シミュレーター環境で MakeCode ブロックが正しく動くかを視認できます。

**講師が準備段階で確認した結果を共有**します。

**講師の説明**:

> テスト ✅ → ビルド ✅ → 実機で確認 ✅
> この 3 段階で、初めて「できた」と言えます。

## 88〜90分: 学習の振り返り

**講師が問いかけ、学習者が答える**（一言～三文で）:

1. **「モックテスト」「シミュレーター」「実機」の違いは？**
   - 期待される答え例：「テストはコンピューター上での実験。シミュレーターは『もし方位角が45度なら』という仮の状況。実機は本物のセンサーを使う」

2. **「カバレッジ100%でもバグがゼロにならない」のはなぜ？**
   - 期待される答え例：「テストしていない値（マイナス、1000度など）があるから」または「テストの期待値が間違っていたら、その間違いは見つからないから」

3. **「今日学んだ3つの言語（ブロック、Python、JavaScript）が全部同じ8方位に分類するのに、なぜ3つも必要？」**
   - 期待される答え例：「ブロックは実機に書き込める。Pythonは細かく書ける。JavaScriptは型で間違いを防げる。それぞれ役割が違うから」

4. **「プログラミングで最後に必ず確認することは何？」**
   - 期待される答え例：「本物の機械（実機）で、実際に動くか目で見て確認する」

**まとめ**:

> プログラミングは「テストで理屈を確認 → テスト成功 → 実際に動かす」の 3 段階です。
> この順番を覚えておけば、もっと複雑なプログラムを書く時も、自信を持ってできます。

## つまずき対応

| 症状 | 確認と対応 |
|---|---|
| `npm` コマンドが見つからない | Node.js がインストールされているか確認。入ってなかったらインストール |
| `uv` が見つからない | Python の管理ツル。Python 3.12 以上がある環境を用意する |
| テストが失敗する | コマンドをコピペした時に **スペースやタイプミス** がないか確認。もう一度最初からやり直す |
| MakeCode Web に接続できない | ネットワークの状況を確認。オフラインなら、シミュレーターだけで進める |
| コンパスが北を向かない | センサーを校正（Aボタン）。校正の時は **磁石・スピーカー・金属から離す** |
| エラーメッセージが読めない | 赤い文字で出ているエラーを講師や友人に見せて一緒に読む |
