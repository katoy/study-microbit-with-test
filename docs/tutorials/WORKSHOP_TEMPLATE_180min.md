### スライド1: 「プログラミングの3つの検証方法」

**講師の説明**:

> - **Python**: 細かい制御ができる。MakeCode と互換
> - **TypeScript**: 「型」で間違いを事前に防ぐ。テストが充実

### スライド2: 「方位磁石センサーの仕組み」

ルートREADMEの「方位磁石とは何か」を見せます。

**黒板に図を描く（または画面表示）:**

```
北（N）を0度として、時計回りに測る

        0°(北)
         ↑
270°←    |    →90°
(西)     |    (東)
        180°(南)
        ↓

8方位への分割:
  0° = 北（N）
 45° = 北東（NE）
 90° = 東（E）
135° = 南東（SE）
180° = 南（S）
225° = 南西（SW）
270° = 西（W）
315° = 北西（NW）
```

**講師の説明**:

> micro:bit には磁気センサーが入っています。地球の磁場を感知して「今どの方向を向いているか」教えてくれます。
> センサーが返す値は「方位角」という0～359の数字です。
> この数字を「8つの方角」に分類するのが、今日のプログラムの目的です。

### 問いかけ1: 「もし 67.5 度だったら？」

**学習者に考えさせる**（手を挙げさせて複数人に聞く）:

> 67.5 度は、北東（NE = 45°）と東（E = 90°）の真ん中です。
> どちらにしますか？

予想される答え：「両方？」「その場合のルールが必要」「どちらかに決める」

**講師の説明**:

> 正解は「ルールを決める」です。今日のプログラムでは、
> **45° 以上 90° 未満なら東北東（NE）** というルールを使います。
> つまり **67.5° は NE ではなく E** です。

### 問いかけ2: 「北だけが特別な理由は？」

**黒板を見せて**:

```
北は 0° を中心に左右に広がる（-22.5° ～ +22.5°）
南は 180° を中心に左右に広がる（157.5° ～ 202.5°）

でも 0° は「0°未満」にならない（方位角は常に 0～359）
だから北は特別に「0° ～ 22.5°」「337.5° ～ 359°」の 2 つの範囲
```

**講師の説明**:

> このように「ルールを正確に作る」ことがプログラミングの大事な部分です。
> ルールを間違えると、プログラムの結果も間違えます。

### 問いかけ3: 「なぜ3つの言語で同じものを作るのか？」

**学習者に考えさせる**（手を挙げさせて複数人に聞く）

予想される答え：「勉強になる」「比較できる」「どれが得意か試す」

**講師の説明**:

> その通り！ 実は、プログラミングの世界では「同じ目的を複数の方法で実装する」ことで、
> 1. どの言語が何に向いているか学べる
> 2. 間違いを複数の角度から見つけられる
> 3. チーム開発で「どの言語を選ぶか」の判断ができる
>
> 今日は「なぜこの3つの言語が選ばれたのか」も考えながら進みます。

**学習者の作業**:

```typescript
test('heading from 0 to 89.9...', () => {
```

3. その下に新しいテストを追加する:

```typescript
test('67.5 度の直前と境界を判定する', () => {
  expect(Compass.headingToDirection(67.49)).toBe('NE');  // 22.5 <= 67.49 < 67.5 => NE
  expect(Compass.headingToDirection(67.5)).toBe('E');    // 67.5 <= 67.5 < 112.5 => E
});
```

4. テストを実行する:

```bash

```

**何が起こるか**:

- ✅ 成功したら、このテストは既に正しく実装されていることが分かります
- ❌ 失敗したら、プログラムにバグがあります

**講師の説明**:

> このテスト 1 つで、グレーゾーン（どちらでもあり得そう）の部分を確実にしました。

**早めに終わった学習者向け**:

`-1`、`360`、`NaN` といった「ありえない値」をテストして、プログラムがどう対応するか確認します。

## 65〜80分: 品質チェック（テストが本当に役に立つか確認）

**講師の説明**:

> テストを書いたら、それが本当に効く（バグを見つける）かテストします。
> 不具合を作って、テストが見つけてくれるか確認しましょう。

**講師の操作**（学習者は見ていても、自分でやってもいい）:

1. 学習用ブランチを作る:

```bash
git checkout -b practice/test-failure
```

2. [`../../projects/sample-compass-ts/test/compass.test.ts`](../../projects/sample-compass-ts/test/compass.test.ts) で、さっき追加したテストの期待値を一時的に間違える:

```typescript
test('67.5 度の直前と境界を判定する', () => {
  expect(Compass.headingToDirection(67.49)).toBe('E');   // ← 意図的に間違える（NE ではなく E）
  expect(Compass.headingToDirection(67.5)).toBe('E');
});
```

3. テストを実行する:

```bash
npm run test:all
```

**何が起こるか**:

```

Expected: E
Received: NE
```

❌ テストが失敗します。

**講師の説明**:

> テストが「本当に間違いを見つけた」ということです。テストがいなかったら、このバグは本番までに気づかなかった可能性があります。

4. 期待値を戻す:

```typescript
test('67.5 度の直前と境界を判定する', () => {
  expect(Compass.headingToDirection(67.49)).toBe('NE');  // ← 正しい値に戻す
  expect(Compass.headingToDirection(67.5)).toBe('E');
});
```

5. テストを実行する:

```bash
npm run test:all
```

✅ 全テスト成功。

**講師の説明**:

> 「テスト → 失敗 → 修正 → 成功」という流れが大事です。
> この循環（サイクル）で、バグは修正され、プログラムは正確になります。

**チェックポイント**: 学習者が「テスト = 間違いを見つける道具」だと理解できているか、言葉で説明させます。

### Part 1: MakeCode Python の実装を読み解く（10分）

**講師の説明**:

> MakeCode ブロックをコンパイルすると Python になります。その Python コードを読んで、
> TypeScript と比べて何が違うのか見てみましょう。

**学習者の作業**:

1. [`sample-compass/src/compass_makecode.py`](../../projects/sample-compass/src/compass_makecode.py) を開く

```python
def heading_to_direction(heading: int) -> str:
```

### Part 1: 「品質ゲート」とは何か（5分）

**講師の説明**:

> 実は、プログラムはテストが通ったら終わりではありません。
> その後、「コード全体が複雑すぎないか」「セキュリティ上の問題がないか」など、複数の**検査**を通す必要があります。
> これを「品質ゲート」と呼びます。

**図解**（黒板またはスライド）:

```
コードを書く
     ↓
テストを実行 ← テストが失敗したら修正
     ↓
「品質ゲート」の検査（複数）
  - テストカバレッジは100%か？
  - セキュリティ上の問題はないか？
  - コードスタイルは統一されているか？
  - 複雑度は高くないか？
     ↓
全てOK → 本番環境へリリース
     ↓
実機で動作確認 → ユーザーが使える
```

**講師の説明**:

> 「品質ゲート」があると、バグは本番まで進みにくくなります。
> 今日は、その品質ゲートを実際に体験します。

### Part 2: 意図的にバグを混入する（5分）

**講師の操作**（学習者は見ていても、自分でやってもいい）:

1. 作業ブランチを作る:

```bash
git checkout -b practice/quality-gate-test
```

2. [`projects/sample-compass-ts/src/compass.ts`](../../projects/sample-compass-ts/src/compass.ts) を編集:

**元のコード**:
```typescript
static headingToDirection(heading: number): Direction {
  if (heading < 0) return 'N';
  if (heading < 45) return 'N';
  if (heading < 90) return 'NE';
  // ... 以下同様
}
```

**バグを混入**:
```typescript
static headingToDirection(heading: number): Direction {
  if (heading < 0) return 'N';
  if (heading < 45) return 'N';
  // ← NE のケースを削除（意図的なバグ）
  if (heading < 90) return 'E';  // ← 45° は NE ではなく E になる
  // ... 以下同様
}
```

3. ファイルを保存。

**講師の説明**:

> このバグは「目で見ただけ」では分かりにくいです。
> でも品質ゲートが自動で見つけてくれます。

### Part 3: テストを実行して検出させる（5分）

```bash
npm --prefix projects/sample-compass-ts test
```

**何が起こるか**:

```
FAIL  test/compass.test.ts

    ✓ should return N for 0 to 45
    ✓ should return N for 337.5 to 360

      Expected: 'NE'
      Received: 'E'
```

❌ テストが失敗。バグが見つかりました。

**講師の説明**:

> テストが「バグを見つけた」ということです。テストなしだったら、このバグは本番環境に行ってしまいました。
> ユーザーが「45 度なのに東（E）と表示される」という変な不具合に気づいて、初めてバグが判明したはずです。

### Part 4: バグを修正してテストに成功させる（10分）

1. コードを元に戻す:

```typescript
static headingToDirection(heading: number): Direction {
  if (heading < 0) return 'N';
  if (heading < 45) return 'N';
  if (heading < 90) return 'NE';  // ← 元に戻す
  // ... 以下同様

```

2. テストを実行:


✅ 全テスト成功。

3. さらに詳細テストを実行:

```bash
npm --prefix projects/sample-compass-ts run test:coverage
```

**何が出るか**:

```
File                    | % Stmts | % Branch | % Funcs | % Lines |
All files               |   100   |   100    |   100   |   100   |
```

カバレッジが 100% ＝ 全てのコード行が最低 1 回はテストされている。

**講師の説明**:

> カバレッジ 100% は「全ての行が実行された」という意味です。
> でも、それでも全てのバグが見つかるわけではありません。テストの「期待値が間違っていたら」、その間違いは見つかりません。

### Part 5: 学習の深掘り（10分）

**学習者に問いかけ**（手を挙げさせて複数人に聞く）:

## つまずき対応

| 症状 | 確認と対応 |
|---|---|
| `npm` コマンドが見つからない | Node.js がインストールされているか確認。入ってなかったらインストール |
| `uv` が見つからない | Python の管理ツル。Python 3.12 以上がある環境を用意する |
| テストが失敗する | コマンドをコピペした時に **スペースやタイプミス** がないか確認。もう一度最初からやり直す |
| MakeCode Web に接続できない | ネットワークの状況を確認。オフラインなら、シミュレーターだけで進める |
| コンパスが北を向かない | センサーを校正（Aボタン）。校正の時は **磁石・スピーカー・金属から離す** |
| エラーメッセージが読めない | 赤い文字で出ているエラーを講師や友人に見せて一緒に読む |
| 応用題の実装が進まない | 「5 つのステップに分ける」とアドバイス。完全な実装を目指さず「試行錯誤のプロセス」を評価 |
| グループメンバーのレベルが違う | 高度なメンバーに「応用題の応用」を提示。初級メンバーに「観察役」を任せて全員参加を確保 |
